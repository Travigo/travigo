# Ordered journey path storage

Use ordered calls as the CTDF journey path. The same CTDF fields persist directly in MongoDB, and the compatibility layer derives legacy legs at the public API boundary. Store all whole-journey and per-leg geometry in the existing `journey_tracks` collection, including tracks used by a single journey. Use BSON dates and descriptive fields with the side-specific stop indexes. Measure compact encoding, index consolidation, and shared patterns against this implementation.

The [sizing notes](journey-path-storage-notes.md) report substantial BSON and collection allocation savings for one bus feed. The main workload to improve is scheduled-journey loading in the tracker and the broad SIRI fallback. Arrival and departure boards, planner, and rail enrichment also depend on the path and need parity checks. This design is based on Travigo `eacc3694` and WebUI `c377fd0`.

## CTDF and MongoDB model

Use the same document shape in `journeys_raw`, `journeys_staging`, and `journeys`. Retain journey identifiers, service, operator, departure time and timezone, availability, dataset ownership and timestamps, expiry, replacement references, amendment stop references, rail metadata, and the optional whole-journey `trackref`. Replace the stored `path` array with `calls`. The array order defines the visits, including repeated stops. On a continuous path, leg `i` starts at call `i` and ends at call `i+1`. The final call has the existing realtime stop index equal to the number of legs.

| Field on a stored call | Meaning |
| --- | --- |
| `stopref` | The original stop reference, including its namespace. Preserve aliases as supplied. |
| `arrival`, `departure` | Existing timetable values as BSON dates, with missing values distinguishable from midnight. Use the old origin arrival when an outgoing leg exists and the incoming destination arrival at a segment end. |
| `platform` | Existing origin platform when an outgoing leg exists, otherwise the incoming destination platform. |
| `originactivity`, `destinationactivity` | Full activity values from the outgoing origin and incoming destination respectively. The two sides can disagree and each can contain both pickup and set-down, pass, or no values. Preserve nil versus empty arrays if the existing API serialises them differently. |
| `incomingarrival`, `incomingplatform` | Overrides for an incoming destination value that differs from the canonical call. An explicitly missing time or empty platform can be an override. Use field presence to distinguish an override from inheritance. |
| `start`, `end` | Sparse structural markers on the first and last calls of each contiguous segment. A segment end has no outgoing leg. A segment start has no incoming leg. Neither flag depends on activity or whether the time is populated. |
| `outgoing` | Optional metadata for the leg to the next call. Holds `destinationdisplay`, `distance`, `trackref`, and ordered `passingpath` TIPLOC references. Omit when empty. |

A three-stop trip stores the intermediate visit once. Its departure board reads its origin-side fields, its arrival board reads its destination-side fields, and its map draws the outgoing geometry. A path `A → B → A` stores three visits, with the two `A` visits at indexes 0 and 2. Equal adjacent stop references can also describe a real leg and are preserved.

CIF skips legs with unresolved endpoints, and OSM enrichment already handles discontinuities. For legs `A → B` and `D → E`, store calls `A, B, D, E` with boundaries at `B` and `D`, then iterate adjacent calls within each segment. Derive legacy occurrence indexes from the number of real connections for these paths. Storage offsets diverge from those indexes after a gap. Count gaps, empty paths, nil legs, and malformed refs in rehearsal. Keep an explicit empty array for supported pathless schedules, which TransXChange can currently write. Treat a missing array on a full read as a schema error. Surface unexpected rejects with dataset and journey identifiers before cutover.

Drop persisted copies of hydrated `Stop` objects from the call design after implementing their read-side replacements. CIF currently embeds them. Detail uses names, coordinates, aliases and provenance, door-side needs platform and track context, and TRUST movement assigns departed and next stop objects from path endpoints. Hydrate these from stop references at their existing read boundaries, batching unique references and cloning any stop object mutated by service-specific name overrides. Verify stop hydration against CIF, including aliases and missing coordinates. Keep a measured BSON control with embedded stops held equal, so removing them is accounted for separately from storing calls.

### Track storage and lifecycle

`journey_tracks` owns the coordinate arrays and their datasource and timestamps. Journeys reference a track by `primaryidentifier`, using top-level `trackref` for a whole shape and `calls.outgoing.trackref` for each leg. `journey_track_routes` continues to describe route and leg matches using track references. Shared calling patterns carry only stop references and structure. Trips with the same stops can reference different tracks. Trips with unique geometry use the same track collection and reference fields as shared ones. Ordered TIPLOC passing references and scalar leg distance remain timetable metadata.

Make geometry exclusion a write invariant. CTDF geometry fields are excluded from BSON. Hydrated geometry can sit alongside an existing reference in memory. If a producer has geometry with no reference, it must persist a `JourneyTrack` and assign its reference before writing. Reject unreferenced geometry at the write boundary so an importer cannot silently lose it. Use a strict collection validator to reject inline geometry, including root `track`, nested `calls.outgoing.track`, and the old `path` field. Create raw, staging and live collections with validation before their first write, including when the linker recreates staging. Verify that validation survives full publication, and exercise both server-side copy modes in rehearsal. [MongoDB `$out` validation](https://www.mongodb.com/docs/manual/reference/operator/aggregation/out/#schema-validation-errors) · [MongoDB `$merge` validation](https://www.mongodb.com/docs/manual/reference/operator/aggregation/merge/#schema-validation)

Use the existing provider and dataset scoped track IDs and indexes. Reuse an ID where the producer knows the track is shared. Allocate a stable ID from the producer's owning journey or route and leg identity for unshared geometry so retries upsert the same track. Write geometry successfully before publishing references. GTFS flushes bounded track batches before writing the journeys that reference them. A track write failure aborts the import before that journey batch is written. On refresh, retain old tracks until the replacement is visible and reference checks allow cleanup. Keep whole-shape fallback when GTFS cannot split the shape. A Darwin path change must drop any whole-journey reference that describes the original route.

When a dataset retires or a generation expires, check whole and leg references across raw, staging and live journeys and track-route metadata. Clear or replace references owned by the retired dataset before deleting its tracks, and preserve geometry still referenced by retained journeys or routes. Use the existing publication ordering or fence concurrent writes before sweeping. Cleanup currently checks MongoDB references. A realtime snapshot can briefly keep a reference to geometry deleted by a regular refresh or retirement, in which case the API uses its no-track fallback. Clear affected realtime state during cutover. Retaining geometry until snapshots expire is a separate lifecycle change. Keep geometry and provenance available together when hydrating from a ref.

Use [CTDF track hydration](../../pkg/ctdf/journeytrack.go) for detail and [the tracker track cache](../../pkg/realtime/vehicletracker/trackcache.go) for vehicle matching and progress. Fetch the distinct refs in batches on paths that need coordinates, including map display and rail geometry consumers. Keep SIRI candidates, stop boards, graph scans and stop-services on schedule data alone. Missing refs should surface in diagnostics and follow existing no-geometry behavior at read time. A persisted dangling ref fails rebuild acceptance. Check realtime-only and synthetic TfL journeys, whose realtime snapshots carry track refs. Where a realtime snapshot must render a whole shape without reloading the static journey, retain the whole-journey ref in that snapshot as well. Hydrated CTDF geometry remains available to the API and WebUI.

### Direct persistence and API compatibility

`ctdf.Journey.Calls` is the canonical path, including for internal consumers and graph responses. Read and write the CTDF type directly. Feed timing links are translated during ingestion. Use call or adjacent-call iteration for schedules, matching, realtime progress, and track enrichment. Preserve the departure graph's packed indexes. A projected path must include stop references and segment boundaries. Header-only lookups retain their current narrow projections.

Journey detail and realtime journey detail default to the existing `Path` leg array. Request `?path_format=calls` to receive the canonical `Calls` array in the same response view. The selected view still controls which nested journeys expose a path and which fields they include. Hydrate tracks and stops before serialization, preserve realtime occurrence indexes, and leave compatibility conversion at the response boundary. Remove the legacy response when clients have moved to calls.

Keep existing GTFS service-day offsets, including over 24 hours, and preserve CIF and Darwin wall-clock resolution across calendar days and DST. Preserve BSON millisecond precision and distinguish missing from a genuine zero offset. Leave the top-level `departuretime` type in place for SIRI exact-clock probing and block and provider lookups. Treat short BSON keys and integer times as independent experiments. An integer encoding needs a single documented, reversible clock representation with room for overflow and subsecond values, plus an explicit missing state. Only compact activities once all current values and output semantics can round-trip. [GTFS Schedule Reference](https://gtfs.org/documentation/schedule/reference/#stop_timestxt)

## Stop query and index design

The current two stop indexes lead with origin or destination stop, then `serviceref` and `_id`. Boards seek by stop, and SIRI can query by stop and service with only `_id` projected. SIRI uses membership on either side across the journey, rather than requiring the two stops on one leg. It rechecks membership on fetch because an import can change a journey between the covered scan and the fetch. Pickup/set-down rules are evaluated separately from the structural memberships. [Current indexes](../../pkg/database/collections.go) · [Current SIRI queries](../../pkg/realtime/vehicletracker/identifiers/siri_stops.go)

1. **Parity baseline.** Derive distinct `originstoprefs` and `destinationstoprefs` from the respective leg sides, or from calls with an outgoing or incoming leg. Give each the existing compound index shape. Maintain them in the same write as calls when structure changes. Track-only mutations leave them alone. This preserves existing covered queries and gives a baseline for comparing read plans and total storage. Keep the amendment-stop and non-path indexes.
2. **Consolidation candidate.** Index `{ "calls.stopref": 1, "serviceref": 1, "_id": 1 }`. One multikey entry per distinct journey/stop replaces two entries where the stop is on both sides. Retain separate SIRI probes when both sides are supplied. With only the union index, ID probes include some wrong-side hits. Recheck the stop and its structural role on the same call before the exact-time probe's limit and before full fallback matching. For example, a departure candidate requires a matching call with no end marker. Use independent conditions for origin and destination, which can match different call elements. Apply the same role checks to single-endpoint SIRI queries, boards, and lazy graph fill before any candidate limit or completeness decision. Compare index-and-filter versus server-side `$elemMatch` for broad scans. The ID-only probe can still be covered for stop membership, while a query using `$elemMatch` needs document examination. Track how often union candidates hit the current 1,024-ID fallback earlier. [MongoDB multikey index coverage](https://www.mongodb.com/docs/manual/core/indexes/index-types/index-multikey/#covered-queries)
3. **Choose on measured behavior.** The sample has 713,018 distinct journey/side/stop keys across the old two indexes and 369,107 distinct journey/stop keys for the union, about 48% fewer entries. The two per-journey arrays in the parity baseline would add 12.61 MiB of BSON to this sample before indexes. Measure actual index bytes and build time separately. At terminal-heavy stops one side can be empty while the union has hundreds of trips. Compare candidate counts and p95/p99 on both sides and for SIRI, plus graph lazy fill. Adopt the union if end-to-end parity and performance hold. The side-specific fields and indexes are the fallback if the union regresses important lookups. A per-journey stop-call lookup collection would introduce row creation, storage and publication/cleanup work proportional to calls. Test it only against a concrete query need that the embedded indexes or pattern lookup fail to meet.

## Sharing across similar journeys

The first sharing candidate is an immutable pattern containing the exact ordered stop reference sequence. Many departures share that sequence even if the journey IDs, schedules, platforms, activities, calendars or displays differ. A short working, express variant, reversed trip, diversion, or changed segment boundary gets its own pattern. Preserve repeated refs and include segment structure in identity if sharing discontinuous paths. Use raw namespaced stop refs and a versioned canonical encoding before hashing. Initially share continuous static trips only. Use the existing [GTFS shape store](../../pkg/dataimporter/formats/gtfs/journey_tracks.go) and [track routes](../../pkg/journeytracks/routes.go) for geometry reuse. Two trips with the same stops can take different tracks, pass different TIPLOCs, or show different displays.

A separate pattern collection would hold `{_id, stops}`. Each shared journey carries `patternref` and its ordered per-call data with the stop refs factored out. Time, side-specific activities and platforms, outgoing metadata, and journey fields stay with the journey. Resolve patterns in bounded batches and cache them as immutable values. Validate equal call counts and version, and treat a missing pattern as a publication or read error with the journey and pattern IDs. Keep VSTP and Darwin inline, along with one-off patterns where referencing costs more. A static reimport or variant creates a new ID if its stop sequence changes. Upsert and verify immutable patterns before inserting referring raw journeys. The linker publishes the references with the journeys. A failed import can leave unused patterns but must not expose dangling references. Reclaim patterns against raw, staging and live references only after active import/publish jobs are fenced, or during a controlled rebuild. Ordinary dataset retirement can leave patterns for the next safe sweep. Where sharing is enabled, keep track cleanup scoped to geometry refs still held by journeys.

| Stop lookup for shared journeys | What it costs |
| --- | --- |
| Store an indexed stop membership array per journey | Keeps direct board and SIRI queries. Duplicates stop refs in the journey and keeps per-journey multikey entries. Role checks still need the pattern and per-call structure unless membership is split by side. |
| Index stop refs on patterns, then fetch journeys by indexed `patternref` | Moves the shared journeys' multikey membership to unique patterns and adds a scalar journey index, potentially compound with `serviceref`. Resolve matching patterns, then fetch journeys for those IDs with the existing service/dataset predicates. Keep the direct indexes for inline journeys and merge their results by document identity. Apply structural side checks before any limit. Both SIRI endpoints may match different occurrences of the same pattern. Batch pattern IDs and journey fetches, benchmark busy-stop fan-out and index plans, and update stop-services building to expand each pattern's memberships for its dataset/service combinations. |
| Share a relative timing profile in addition to stop refs | Requires the same stop sequence and exactly equal arrival/departure offsets, with the same clock convention, precision and missing state. Resolve journey base time with overflow and DST semantics. Avoid approximating run or dwell time. Defer until exact sharing is measured on bus and rail. |

For short workings, 171 of the 800 sequences were contiguous slices of a longer sequence, covering 1,113 trips. Sharing those slices would save at most 4,131 stop refs across the unique pattern documents, before storing offsets and lengths. Queries would also have to check that the matched stop occurs inside the slice, on the correct side of its boundaries. Keep each variant as its own pattern for the first comparison. For diversions and overlapping routes, existing leg geometry references already allow reuse without sharing the passenger call sequence.

### What it would save on the sample

Re-encoded the 12,598 existing NDJSON rows using the Go MongoDB driver's Extended JSON and BSON encoders, including an ObjectID field on each journey. These are logical BSON totals. The control removes empty/null embedded stops, platforms, distance and track from legs while keeping the other data. The sharing calculation moves just the stop refs into one copy per exact sequence and includes each pattern document with a 32-byte binary ID and a matching reference on each journey. It uses the sample's existing plain and compact prototypes. The sample has continuous paths, six repeated visits and no differing adjacent arrival clocks. Production fields, structural markers, index data, and compression are outside these calculations.

| Representation | Logical BSON | Comparison |
| --- | ---: | --- |
| Original legs | 118.08 MiB | Baseline |
| Legs with sampled empty fields removed | 85.10 MiB | 27.9% below original legs |
| Plain inline calls | 53.05 MiB | 37.7% below trimmed legs |
| Plain calls with shared stop sequences | 45.96 MiB | 7.08 MiB below plain inline calls (13.3%) |
| Compact inline calls | 21.57 MiB | 74.7% below trimmed legs |
| Compact calls with shared stop sequences | 16.60 MiB | 4.97 MiB below compact inline calls (23.0%) |

There were 800 exact stop sequences, 801 when scoped by service and direction, and 147 singleton sequences. The median pattern was used by nine journeys. Grouping by exact sequence and timetable clock offsets yielded 6,783 distinct groups before any check of activity or geometry, so sharing timing profiles has fewer opportunities in this sample. Unique pattern/stop memberships numbered 24,077, compared with 369,107 journey/stop memberships. The pattern-based lookup still needs the scalar journey index and a query to expand matching patterns to trips.

A deduplicated per-journey `stoprefs` array adds about 6.43 MiB of BSON to either sharing prototype. That leaves about 0.66 MiB of document savings for plain calls and makes compact shared calls about 1.46 MiB larger than compact inline calls, before indexes. Treat the storage benefit and extra lookup cost as a joint decision. Measure a second collection's allocation and indexes with the same MongoDB settings before estimating disk savings. The original 13/20 GiB production allocation scenarios cover inline formats on the bus sample ratios and do not incorporate the control, this design's full fields, or pattern indexes. ### Initial implementation measurement

Re-imported the same 12,598 bus journeys into isolated MongoDB 8.0 using direct CTDF BSON, including segment markers and both role arrays. Each collection had the default `_id` index, a journey identifier index, and the stop indexes shown below. These allocation figures describe this run and index set.

| Layout | BSON | Allocated collection | Indexes | Combined allocation |
| --- | ---: | ---: | ---: | ---: |
| Original legs, two stop indexes | 118.08 MiB | 24.00 MiB | 7.12 MiB | 31.12 MiB |
| Trimmed legs, two stop indexes | 85.10 MiB | 16.06 MiB | 7.11 MiB | 23.17 MiB |
| Implemented calls, two role indexes | 69.50 MiB | 11.45 MiB | 7.04 MiB | 18.48 MiB |
| Calls with a union index and no role arrays | 56.88 MiB | 9.64 MiB | 3.76 MiB | 13.40 MiB |

The implemented layout saved 20.2% in combined allocation against trimmed legs. A stop/service probe for `stop-646` and `route-6612` examined 42 keys and zero documents on the origin-role index. The union index examined 86 keys and zero documents before checking the role. The implementation keeps the two role indexes for existing board and SIRI behavior. The union index, compact encoding and shared patterns remain benchmark candidates pending representative rail and mixed-workload results.

An indexed, serial tracker read of each sampled journey returned an average of 9,595 bytes of projected BSON for original legs, 6,850 for trimmed legs, and 4,345 for calls. The calls projection excludes the role arrays, so it returned 36.6% fewer bytes than trimmed legs. Median BSON decode time was 67, 43, and 37 microseconds respectively. These are uncompressed BSON sizes and timings from one interleaved pass on a local bus-only database. The test excludes track hydration and does not establish cold-cache behavior, end-to-end latency, or sustainable production throughput.

An isolated MongoDB 8 rehearsal imported and published the full TransLink GTFS feed (62,990 journeys) and rebuilt 14,711 stop/service pairs. Raw and published journeys had no inline tracks or missing calls. All 28,991 distinct referenced tracks resolved in `journey_tracks`. With the feed's stops loaded as fixtures, the departure graph rebuilt one day from MongoDB: 25,823 journeys, zero rejected journey-days, and 171 journeys returned for the sampled stop.

A separate loop fixture loaded through the API rendered in the existing WebUI, including the repeated stop, separate arrival and departure times, and a leg without geometry. Both API formats returned the expected stop order and hydrated the leg that had a track. These checks cover a bus feed and a focused WebUI fixture; rail and mixed-load cutover checks remain part of rehearsal.

1. **Round trips through actual writes and projections.** Use fixed feed inputs for ordinary bus, TransXChange timing links, rail CIF and VSTP, NYC GTFS, Darwin changes, and synthetic TfL. Include first/last, repeated and adjacent same-stop visits, alias refs, short workings, unresolved-stop gaps, missing times versus midnight, overnight services, spring and autumn DST, differing platforms and times between sides, every current activity, and complete geometry including passing points. Run importer, linker, enrichment, retirement, and dynamic upsert/withdrawal on an isolated MongoDB database. Verify decoded leg fields, reference hydration and projected reads, replacement/expiry behavior, and call/index consistency. Compare public fixtures including legs, occurrence IDs, arrival and departure rows and ordering, journey detail including map and realtime-only, planner results and amendments, saved views, subscriptions and events.
2. **Verify geometry storage and hydration.** Exercise a shared leg track, a unique track, a split shape, a whole-shape fallback, and composed rail geometry. Check direct writes, both publish modes, enrichment retries, injected track-write failure and dataset retirement. Assert that raw, staging and live contain zero inline geometry and every stored track ref resolves to a usable track. Verify map geometry and provenance, vehicle matching, and rail door-side or position behavior on the same inputs.
3. **Measure each proposed storage layout on equal data.** Use original legs, empty-field control, descriptive calls, compact calls, and calls with shared patterns and their required indexes. Hold geometry storage equal when isolating the effect of changing path shape. Report `journey_tracks` collection and index bytes alongside the journey collections so geometry moved out of journey documents is accounted for. Keep embedded-stop, activity and time encoding changes isolated. Record staging peak, import and publication time, index build time, working set, and graph/stop-services rebuild time. Include buses, long/heavily enriched paths, and rail. Run through representative mixed-workload concurrency and repeat warm and cold measurements.
4. **Replay production-shaped reads.** Compare tracker cache misses and hits, stop and track hydration, SIRI exact/ambiguous/no-match including broad fallback, busy arrivals/departures including terminal-only and looping paths, cold graph lazy fills, and planner scans. Record returned BSON, MongoDB keys/documents examined and query plans, CPU, allocation and retained heap, cache hit rate, database round trips, and p50/p95/p99 latency and sustainable throughput. Use the supplied broad SIRI and GTFS-RT burst as workload references, and verify selected journey IDs, occurrence indexes and user-visible results on the same input.
5. **Select the release format.** Require semantic parity, a material reduction in total allocated journey storage with the production query indexes, and no material regression in tracker/SIRI tail latency, busy boards, or planner readiness on the rehearsal workload. Record the baseline and acceptance thresholds before comparing options. Ship sharing or compact encoding in this rebuild only if they justify their incremental operational and read costs. Inline descriptive calls give a working design independently of those choices.

## Downtime rebuild

Run the change as one coordinated format cutover. There is no legacy reader, dual write, or document conversion. Preserve stable journey identifiers where source data and import logic allow so saved journeys, links and subscriptions can resolve after the rebuild. Scope the reset to timetable data and its derived state. Keep unrelated user data if retaining that database.

1. Rehearse the sequence on a clean database with the same app images and indexes. Retain the previous deployable build and the source feed versions needed for rollback. Record which VSTP/Darwin inputs are replayable and any gaps where live state must refill from feeds.
2. Start downtime, suspend batch schedules, drain or stop active importer, linker and track jobs, and stop scheduled-path readers/writers together, including API workers, tracker, graph and rail realtime consumers. Fence old jobs and account for queued messages so they cannot republish old-format records or replay stale occurrences into the new state.
3. Recreate the journey collections with validators and indexes for the chosen schema, and the shared pattern collection if selected. Reset or force the affected import and publication generation state so freshness, ETag, file hash and feed-version checks cannot skip missing data. Reimport the source timetable and dependent stops, services, operators, transfers and track inputs as needed. Run pre-publication track enrichment, publish with the existing linker, then run any post-publication enrichment the batch plan requires. Verify expected datasets and coverage, importer rejects, schema, indexes, and track/pattern references. Require zero inline geometry and zero unresolved track refs in every journey collection before reopening traffic. Confirm the journey indexes exist with the new keys before reopening traffic. Journey index creation failures stop the importer; the downtime rebuild recreates the collections so old indexes with the same names are removed with them.
4. Rebuild stop-services and the departure graph against the new publication. Start the graph with a fresh snapshot location or remove the old snapshot from use, including its Mongo scan cursor. Invalidate timetable-derived board and matching caches, process-local tracker caches and stale realtime run/occurrence state, without flushing unrelated Redis data. Restore or refill realtime state and replay valid VSTP/Darwin inputs where available. Check amendment parents, no orphan references, graph completeness for the configured window and supported fallbacks, and populated busy stops.
5. Run end-to-end checks with the actual API and WebUI. Reopen traffic and resume normal publication and realtime schedules once checks pass. If the cutover fails, repeat the downtime sequence with the previous image and restore or reimport the previous format, then rebuild its derived state. Include reimport and graph warm-up time in the outage estimate.
